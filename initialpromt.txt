# Build a Production-Ready Web-to-PDF Application

You are a senior full-stack engineer. Build a production-ready MVP web application that converts any public web URL into a clean, printable, properly paginated A4 PDF.

The application must load the target website as a real browser would, execute JavaScript, wait for dynamic content, remove unwanted UI/reklama/popups, optimize the page for printing, generate an A4 PDF with intelligent pagination, and provide an interactive preview/editor before the user saves the final PDF.

The workflow is session-based. Do NOT build document history, user accounts, permanent document storage, or a database for saved documents at this stage.

---

# 1. Product Goal

The user enters a web URL.

The application then:

1. Opens the URL in a real Chromium browser using Playwright.
2. Loads and renders the entire page.
3. Executes JavaScript.
4. Handles lazy-loaded content and images.
5. Waits for dynamic content to stabilize.
6. Removes ads, popups, cookie banners, overlays, floating widgets and other unwanted UI.
7. Prepares a clean print version.
8. Generates an A4 PDF using intelligent pagination.
9. Shows the cleaned web page in an editable preview.
10. Shows the generated PDF in a PDF preview.
11. Lets the user manually remove/restore/hide elements.
12. Regenerates the PDF after edits.
13. When the user is satisfied, provides the final PDF for download.

The key objective is:

> Preserve the meaningful content of the webpage while producing a professional, readable A4 PDF with no unwanted advertisements, overlays or clipped content.

Do not create a simplistic `page.pdf()` wrapper. Build a real webpage preparation and pagination pipeline.

# 5. Session-Based Workflow

No authentication.

No persistent history.

No database requirement.

Each conversion exists only for the current session.

A session should contain:

* source URL
* rendered page state
* cleaned DOM representation
* removed elements
* hidden elements
* user modifications
* current PDF
* current settings

When the session expires, its temporary data may be removed.

Use sensible size and timeout limits.

# 6. URL Validation and SSRF Protection

This is mandatory.

The server must NEVER blindly request arbitrary internal network resources.

Before Playwright opens a URL:

Block:

* localhost
* 127.0.0.0/8
* 0.0.0.0
* private IPv4 ranges
* private IPv6 ranges
* link-local addresses
* cloud metadata endpoints
* internal hostnames
* file://
* data://
* javascript://
* other dangerous protocols

Validate:

* protocol must be HTTP or HTTPS
* hostname
* DNS resolution
* redirects
* final destination after redirects

Re-check destination after every redirect.

Protect against DNS rebinding where practical.

Add:

* request timeout
* navigation timeout
* maximum redirects
* maximum response size
* maximum page processing time

Never expose server filesystem paths or internal errors to the user.

---

# 7. Full Page Loading

Do NOT treat `DOMContentLoaded` alone as page completion.

The browser service must:

1. Navigate to the page.
2. Wait for initial DOM.
3. Wait for network activity to settle.
4. Allow JavaScript execution.
5. Wait for images and important fonts.
6. Detect dynamically inserted content.
7. Scroll through the page progressively to trigger lazy loading.
8. Continue scrolling until content stops increasing.
9. Wait again for network activity and layout stabilization.
10. Perform a final layout pass.

Support pages built using:

* React
* Vue
* Angular
* Next.js
* other JavaScript-heavy frameworks

The implementation must be robust against:

* lazy-loaded images
* infinite-scroll content
* delayed content
* dynamically inserted components
* client-side rendering

However, enforce limits to prevent pages with infinite loading from hanging forever.

Possible safeguards:

* maximum total scroll iterations
* maximum page height
* maximum execution time
* stop if page height/content remains unchanged for several cycles

# 8. Image Loading

Images are critical.

For every relevant image:

* wait for it to load
* support normal `src`
* support lazy-loading
* support `srcset`
* resolve the final loaded image
* preserve aspect ratio
* prevent accidental cropping
* prevent overflow outside printable content

Before PDF generation, verify that images have valid dimensions.

Images must not be cut in the middle merely because of page boundaries when a reasonable alternative exists.

Prefer:

```css
break-inside: avoid;
page-break-inside: avoid;
```

for image-containing blocks.

Large images should be scaled proportionally.

If an image is too large to fit on a normal page, intelligently scale it to fit within printable A4 width.

For exceptionally tall images or infographics, use an intelligent strategy that avoids destructive cropping.

# 14. A4 PDF

The PDF output must use A4 paper.

Use portrait as the default.

Allow landscape only if configured later; do not make landscape the default.

Use dimensions corresponding to true A4:

210mm × 297mm

Set sensible print margins.

Do NOT create a single giant PDF page containing the entire webpage.

The webpage must be paginated into normal A4 pages.

---

# 15. Intelligent Pagination

This is one of the most important parts of the implementation.

Do not simply let Chromium cut the page anywhere.

The pagination algorithm should try to preserve semantic blocks.

Avoid splitting:

* images
* image + caption groups
* headings from their following content
* table rows
* cards
* code blocks
* blockquotes
* lists where reasonably possible
* figures
* captions
* important UI groups

Prefer CSS:

```css
break-inside: avoid;
page-break-inside: avoid;
break-before: auto;
break-after: auto;
```

But do not rely entirely on CSS.

Build a layout analysis layer that detects meaningful block boundaries.

If a block does not fit in the remaining space:

* move the entire block to the next page when possible
* if the block itself is larger than one A4 page, use a controlled split strategy

Never allow accidental clipping.

---

# 16. Headings

Avoid orphaned headings.

A heading should not appear as the last line on a page while its associated content begins on the next page.

Use:

```css
break-after: avoid;
page-break-after: avoid;
```

and/or equivalent layout logic.

For important headings, try to keep at least one following content block on the same page.

---

# 17. Images and Page Boundaries

Never create situations like:

Page 1:
half of a photo

Page 2:
other half of the photo

unless there is absolutely no practical alternative because the image itself is larger than one page.

Normally:

* move image to next page
* preserve complete image
* scale image proportionally

Do not distort aspect ratio.

---

# 18. Tables

Tables need special handling.

Requirements:

* preserve table layout
* prevent horizontal overflow
* scale wide tables when possible
* repeat table headers on subsequent pages when possible
* avoid splitting individual rows when practical
* prevent clipping

If a table cannot reasonably fit at normal scale:

* reduce font size/scale within reasonable bounds
* reduce width proportionally
* use landscape only if that option is explicitly enabled later

For MVP, keep A4 portrait as the default behavior.

* avoid horizontal clipping

Large code blocks may split vertically between pages.

Do not split individual lines horizontally in a way that makes code unreadable.

# 32. Preview Isolation

Because the source webpage is untrusted, never allow arbitrary source-page JavaScript to execute in the application UI.

The cleaned preview must be isolated.

Possible solution:

* sanitized DOM
* isolated iframe
* sandboxed iframe
* disabled scripts
* controlled resource loading

The preview editor needs to manipulate the DOM, but the original page's JavaScript must not gain access to the parent application.
